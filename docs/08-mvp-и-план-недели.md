# MVP и план на неделю

**Команда:** «Дискреция творца»
**Срок:** 7 дней
**Разработка:** весь код — один поток. Команда параллельно ведёт документацию, презентацию, видео и питч.
**Развёртывание:** `docker compose up` — одна команда.

---

## 0. Несущая идея: троичное состояние

Всё решение строится на том, что состояние канала имеет **три** значения, а не два.

| Трит | Состояние | Откуда берётся |
|---|---|---|
| **+1** | отклонение | `СРАБОТКА`, `ОТКАЗ`, выход числа за персональную норму |
| **0** | неизвестно | `Неопределен`, канал молчит, датчика нет на объекте, канал без паспорта |
| **−1** | норма | `НОРМА`, число внутри персональной нормы |

Это не стилистический выбор. В данных 7,5 млн событий `Неопределен`, тепловых датчиков нет
на 13 объектах из 16, датчиков затопления — на 8 из 16, и 1 142 канала вовсе без паспорта.
Бинарная кодировка обязана округлить всё это до «нормы» — и именно так сервис начинает врать.

### Операции

Логика Клини на порядке `−1 < 0 < +1`:

| Операция | Формула | Смысл |
|---|---|---|
| Подтверждение домена | `min(t₁, t₂)` | тревога засчитывается, только если подтверждена соседом |
| Эскалация | `max(t₁, t₂)` | достаточно любого источника |
| Отрицание | `−t` | |

Правило «логических доменов», которое дал заказчик, ложится в `min` дословно:

- `min(+1, −1) = −1` — сосед в норме, одиночную тревогу не засчитываем
- `min(+1, 0) = 0` — **соседа нет или он не наблюдаем → «не знаю», а не «нет»**

Второй случай и есть та честность, которую бинарная логика теряет.

### Где триты НЕ применяем

Троичные нейросети (веса в {−1,0,1}) — это про сжатие моделей, к нашей задаче отношения не имеют
и за неделю не делаются. Триты у нас — слой представления и логики. `RandomForest` принимает
признаки в {−1,0,+1} нативно, причём `0` для него осмысленное значение, а не пропуск.
Выигрыш — в честности и объяснимости, а не в метрике. Так и формулируем в документации.

## 1. Границы MVP

### Входит

**Данные**
1. ETL: CSV → Parquet → витрина. Дедупликация, маска провалов сбора, дебаунс heartbeat < 60 с
2. Семантический контракт (32 строки, покрытие 100 % объёма) → трит-кодирование
3. Исключение артефактов: май 2021 / база 847, массовые базо-дни
4. Ключ локации: `ид_объект` → пикет

**Модели** (четыре сценария ТЗ)
5. **M1 «Отказ канала на 24 ч»** — supervised, настоящие метки, честные Precision/Recall
6. **M2 «Подтопление»** — аномалия частоты пусков + **каскад по разуклону** (сценарий заказчика)
7. **M3 «Пожар»** — многофакторный детектор, отсев прогонов ТО
8. **M4 «Проникновение»** — правила: движение при режиме охраны, ночное окно, мультисенсорность
9. Логические домены на тритах — сквозной слой подавления шума

**Объяснимость**
10. Вклады признаков (декомпозиция путей RandomForest, тест «сумма = скор»)
11. Карточка вердикта: что / почему / что это НЕ / чего мы не видим
12. Контрфакт: «риск упадёт до X %, если Y вернётся к норме»

**Интерфейс (NiceGUI)**
13. Дашборд с уровнями риска, лента вердиктов с фильтром по сценарию
14. Карточка вердикта
15. **Линейная схема коллектора** по пикетам (1 пикет = 10 м)
16. Журнал прогнозов с историей отработки
17. **Квитирование**: непросмотренный вердикт визуально выделен, пока диспетчер его не отработал
18. Форма фиксации решения + справочник причин
19. Админка: пороги Precision/Recall, горизонт, частота оповещений — **настройки, не константы**

**Инфраструктура**
20. REST API
21. PostgreSQL — оперативный контур: вердикты, решения, заявки, пользователи, аудит
22. RBAC: техник → диспетчер района → диспетчер ОДС → группа реагирования
23. Аутентификация: локальная + TOTP, LDAP за интерфейсом-заглушкой
24. `docker compose up` с предобученными весами и seed-данными
25. Кнопка переобучения + версионирование моделей
26. Отчёты XLSX

**Документация**
27. Пояснительная записка: методы, ограничения, архитектура, сборка
28. **Таблица соответствия ТЗ** со статусом и обоснованием каждого отклонения
29. Видеодемонстрация + демо-стенд по ссылке

### Не входит — и это фиксируется письменно

| Отрезаем | Обоснование |
|---|---|
| Мобильное приложение и адаптив | снято организаторами со встречи |
| Реальный LDAP/AD | интерфейс реализован, подключение к каталогу заказчика вне контура |
| Реальные интеграции СМВУ и ОДС | «не интегрированы и не будут», разрешены моки |
| TLS | терминируется реверс-прокси, описан в развёртывании |
| Географическая карта | геоданных нет, разрешена синтетическая линейная схема |
| Реестр оборудования как сущность | не существует у заказчика, строим суррогат из поведения |
| Онлайн-дообучение | достаточно механизма, подтверждено на встрече |
| Резервное копирование и восстановление | регламент эксплуатации, описан в документации |

**Каждая строка этой таблицы обязана попасть в пояснительную записку с обоснованием.**
Невыполненное и необъяснённое = снятие по формальному признаку.

## 2. План по дням

Принцип: **работающий сквозной срез к третьему дню**, дальше наращиваем. Если что-то поедет,
у нас в любой момент есть демонстрируемый продукт, а не полуфабрикат.

### День 1 — Данные

- Конвейер ETL, витрина канало-суток и объекто-суток
- Семантический контракт в коде, трит-кодирование
- Маски: провалы сбора, май 2021, массовые базо-дни
- Поведенческий тест каналов-тёзок (9 % каналов) → правило схлопывания
- Таблица логических доменов из корреляции каналов внутри пикета

**Выход:** воспроизводимая витрина + дата-контракт.
**Команда:** раздел документации «Описание данных и методов обработки» — материал уже собран в `docs/01`.

### День 2 — Признаки и главная модель

- Признаки с шаблонами фраз (список из аудита, ~40 штук)
- Таргет M1, проверка баланса классов
- Обучение M1: RandomForest + LogisticRegression, временной сплит, группировка по (объект, месяц)
- Слой объяснимости: вклады, карточка улик, контрфакт

**Выход:** M1 с метриками и объяснением.
**Команда:** структура презентации, раздел «Постановка задачи и выбор целевой переменной».

### День 3 — Сквозной срез

- Docker-compose: приложение + PostgreSQL, схема оперативного контура
- Скелет NiceGUI: дашборд, лента, карточка вердикта
- REST API
- **Контрольная точка: `docker compose up` → видна карточка вердикта M1 с обоснованием**

**Выход:** работающий продукт end-to-end.
**Команда:** черновик пояснительной записки, таблица соответствия ТЗ.

### День 4 — Подтопление и пожар

- M2: персональная сезонная норма, robust z-score, каскад по разуклону
- M3: многофакторный детектор, отсев прогонов ТО, проверка на 11 кейсах
- Линейная схема по пикетам

**Выход:** три сценария в ленте.
**Команда:** сценарии для видео, скриншоты.

### День 5 — Проникновение, домены, решения диспетчера

- M4: правила, контроль исправности канала охраны, ночное окно
- Логические домены на тритах — сквозной слой
- Квитирование, фиксация решения, справочник причин
- Журнал прогнозов

**Выход:** все четыре сценария + замкнутый цикл накопления разметки.
**Команда:** текст презентации, тезисы питча.

### День 6 — Обвязка и полировка

- RBAC четыре роли, вход с TOTP
- Админка настроек: пороги, горизонт, частота
- Отчёты XLSX, кнопка переобучения
- Полировка интерфейса: понятность без инструкции даёт балл

**Выход:** MVP закрыт целиком.
**Команда:** финальная документация, инструкция по развёртыванию.

### День 7 — Сдача и буфер

- Проверка развёртывания с нуля на чистой машине
- Видеодемонстрация, демо-стенд по ссылке
- **Загрузка пакета с запасом минимум в сутки**
- Буфер на то, что поедет

## 3. Риски недели

| Риск | Что делаем |
|---|---|
| Не хватит времени на все четыре сценария | M1 и M2 — приоритет, они сильнее всего обеспечены данными. M3 и M4 деградируют до правил без ухудшения честности |
| Обучение упрётся в 16 ГБ ОЗУ | витрины вместо полных сканов, `memory_limit` и spill-to-disk — проверено на аудите |
| Docker не соберётся у экспертов | предобученные веса и seed-данные внутри образа, проверка на чистой машине в день 7, плюс видео и демо-стенд как страховка |
| Поздняя загрузка | внутренний дедлайн на сутки раньше официального |
| Приоритет НСД | заказчик сам понизил его; при нехватке времени режем первым |
