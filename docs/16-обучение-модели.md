# 1. Что здесь обучается

В проекте четыре сценария, но обучаемая модель одна.

| Сценарий | Метод | Требует обучения |
|---|---|---|
| **M1 отказ датчика** | RandomForest с настоящей разметкой | **да** |
| M2 подтопление | аномалия частоты пусков к личной норме | нет |
| M3 задымление | многофакторный детектор с отсевом прогонов ТО | нет |
| M4 проникновение | правила по режиму охраны и мультисенсорности | нет |

Такое разделение продиктовано данными, а не выбором: разметки инцидентов
в журнале нет, и организаторы это подтвердили. Целевая переменная есть
только у отказов — она выводится из семантики значений канала.

Поэтому «обучение модели» в этом документе означает **M1**. Детекторы
M2–M4 пересчитываются вместе с витринами и отдельного обучения не требуют.

Обученная модель лежит в репозитории: `models/m1_failure.pkl`, 25,8 МБ.
Она нужна, чтобы пересчитать вердикты и воспроизвести метрики, а собрать
её заново можно только имея на руках датасет на 16 ГБ.

# 2. Что потребуется

| Ресурс | Требование |
|---|---|
| Датасет | 16 ГБ распакованных CSV в каталоге `dataset/` |
| Оперативная память | 16 ГБ (конвейер написан под этот предел) |

сбрасываются на диск. Весь конвейер проходит на ноутбуке; так он
и разрабатывался.

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
unzip dataset.zip -d dataset
```

# 3. Обучение с нуля

Шесть шагов. Замеры — с машины разработки, 16 ГБ ОЗУ.

## Шаг 1. Журнал в Parquet

```bash
python -m scripts.00_import_journal
```

Восемь годовых выгрузок переводятся в колоночный формат: 16 ГБ текста
превращаются в 1,9 ГБ Parquet. Ожидаемый вывод:

```
  2019:   20 993 328 строк  →    133 МБ  (2 с)
  ...
всего 313 546 016 событий
```

**Что проверить:** итог должен быть 313 546 016 событий. Другое число
означает, что распакован не тот датасет или выгрузка неполная.

## Шаг 2. Витрины

```bash
python -m scripts.01_build_marts
```

Около **11 секунд** на все витрины. Здесь же срабатывает защита от старой
ловушки: в справочнике каналов есть переводы строк внутри значений, и
наивное чтение даёт 11 517 строк вместо 11 485. Скрипт падает с внятным
сообщением, если число не сошлось.

**Что проверить:** `dim_channel` — 11 485 каналов, `fact_channel_day` —
4 273 083 строки.

## Шаг 3. Тёзки и логические домены

```bash
python -m scripts.02_twins_and_domains
```

Поведенческий тест каналов с одинаковыми именами и таблица доменов
подтверждения.

**Что проверить:** 1 036 каналов-тёзок в 412 группах, 3 759 доменов.

## Шаг 4. Обучение

```bash
python -m scripts.03_train_m1
```

Меньше минуты. Скрипт печатает размеры выборок, метрики на отложенном
периоде, достижимость целевых значений ТЗ, важность признаков и —
обязательно — проверку точности объяснения.

**Что проверить в выводе:**

```
обучающая:     760 000 строк, позитивов 7 500
отложенная:  4 520 313 строк, позитивов 2 401
период обучения 2022-01-01..2024-12-31, проверки 2025-01-01..2026-06-30

  сумма вкладов равна предсказанию: да   (максимальное расхождение 9.99e-16)
```

Последняя строка важнее метрик. Если она говорит «НЕТ», объяснения
в карточках расходятся с решением модели, и такую модель ставить нельзя
ни при каких метриках.

На выходе: `models/m1_failure.pkl` и `models/m1_metrics.json`.

## Шаг 5. Кривая по горизонтам (необязательно)

```bash
python -m scripts.04_horizon_sweep
```

Обучает ту же модель на горизонтах 24 часа, 3, 7 и 14 суток. Нужна,
чтобы показать: целевая точность ТЗ достигается, но на другом горизонте.
Четыре обучения подряд, несколько минут.

## Шаг 6. Вердикты и агрегаты

```bash
python -m scripts.05_generate_verdicts   # вердикты → deploy/seed_verdicts.json
python -m scripts.10_recall_math         # цена полноты → models/recall_math.json
python -m scripts.09_build_analytics     # агрегаты диаграмм → deploy/seed_analytics.json
```

Первый скрипт считает вердикты по всем четырём сценариям на последние
сутки данных и складывает их в компактный JSON — именно он уезжает
в образ. Второй меряет, сколько предупреждений в сутки требует заданная
полнота. Третий собирает величины для диаграмм.

**Порядок здесь значим.** Сборка агрегатов читает готовые файлы кривой
горизонтов и цены полноты, поэтому её запускают последней. Если поменять
местами, диаграммы покажут прежние числа при новой модели — и это
не будет видно ни по какой ошибке.

**Что проверить:** 162 вердикта, из них 120 отказов, 20 задымлений,
13 проникновений, 9 подтоплений; 13 мультикарточек по объектам.

# 4. Как читать метрики

Эталонные значения поставляемой модели — в `models/m1_metrics.json`:

| Метрика | Значение | Как понимать |
|---|---|---|
| Позитивов в проверке | 2 401 | отказов на отложенном периоде |
| Базовая частота | 0,053 % | один отказ на 1 900 канало-суток |
| PR-AUC | 0,0109 | главная метрика при таком дисбалансе |
| ROC-AUC | 0,807 | здесь почти бесполезна, см. ниже |
| Precision@50 | 0,14 | |
| Precision@100 | **0,16** | в 301 раз плотнее случайного выбора |

**ROC-AUC не показатель.** При доле позитивов 0,05 % он выглядит прилично
и у бесполезной модели. Смотреть нужно на PR-AUC и на precision@k.

**Precision@k считается по всей отложенной выборке**, а не за сутки.
Precision@100 = 0,16 означает: среди ста самых уверенных прогнозов
за восемнадцать месяцев шестнадцать оказались настоящими отказами.
Это один прогноз в пять суток, а не сто в день. Пересчёт в суточную
нагрузку — в разделе 6.4 пояснительной записки.

**Что считать поводом насторожиться:**

* precision@100 ниже 0,08 — модель хуже, чем была; проверьте, не изменился
  ли период обучения и не попали ли в выборку массовые базо-дни;
* PR-AUC близок к базовой частоте — модель не лучше случайной;
* проверка аддитивности не прошла — брак, ставить нельзя.

# 5. Воспроизводимость

**Одинаковый запуск даёт байт в байт одинаковую модель.** Это проверяется
просто:

```bash
python -m scripts.03_train_m1 && cp models/m1_failure.pkl /tmp/run1.pkl
python -m scripts.03_train_m1 && cmp /tmp/run1.pkl models/m1_failure.pkl
```

Так было не всегда, и эту историю стоит знать. Сначала выборка бралась
запросом без сортировки: DuckDB читает параллельно и порядок строк между
прогонами не сохраняет, а лес берёт бутстрап-выборки в порядке поступления
строк. Итог: **одно и то же обучение с одним и тем же случайным зерном
давало разные модели** — два прогона подряд дали precision@100 0,16 и 0,09.

Лечится одной строкой — явным `ORDER BY channel_id, d` в запросе выборки.
Стоит это секунд сортировки и снимает вопрос целиком.

Оговорка о поставляемой модели: она обучена **до** этого исправления,
поэтому повторное обучение даст другую модель — сопоставимую по качеству,
но не ту же самую. Начиная с этой версии кода любая новая модель
воспроизводится точно.

# 6. Дообучение

Под этим словом обычно имеют в виду две разные вещи.

## 6.1. Переобучение на свежих данных

То, что доступно сегодня. Появилась новая выгрузка журнала — сдвигаем
границы периодов в `core/model.py`:

```python
TRAIN_FROM, TRAIN_TO = "2022-01-01", "2024-12-31"
TEST_FROM,  TEST_TO  = "2025-01-01", "2026-06-30"
```

и проходим шаги 1–4 заново. Правило одно и нарушать его нельзя:
**проверочный период всегда позже обучающего**. Случайное разбиение
здесь недопустимо — соседние сутки одного канала почти одинаковы,
и модель запомнит канал вместо того, чтобы выучить деградацию.
Метрики при этом вырастут, а на реальной работе это никак не скажется.

## 6.2. Обучение на решениях диспетчеров

То, ради чего в сервисе ведётся журнал решений, — и чего в конвейере
пока нет. Скажем прямо: **таблица `decision` сегодня в обучении
не используется**. Разметка берётся из данных, а решения накапливаются
в оперативном контуре и ждут своего часа.

Почему так: чтобы учиться на отметках «ложное срабатывание» и
«неисправность подтверждена», их нужны тысячи, а на новом стенде
их ноль. Пары «вердикт — решение» начинают копиться с первого дня
эксплуатации; через несколько месяцев работы района их хватит,
чтобы перевести детекторы M2–M4 с правил на обучение — и это
единственный способ получить разметку инцидентов, которой сегодня
нет ни у нас, ни у заказчика.

Что для этого уже готово: справочник причин с флагом «ложное»,
фиксация решения с автором и временем, журнал прогнозов, связь
вердикта с решением. Чего не хватает: собственно шага обучения,
который читал бы `decision` и строил по ней целевую переменную.

# 7. Обновление модели на стенде

Порядок, который не оставляет стенд в несогласованном состоянии.

## Шаг 1. Обучите и проверьте

```bash
python -m scripts.03_train_m1
```

Сравните метрики с прежними (`models/m1_metrics.json` в git). Если
precision@100 заметно просел — разберитесь до того, как обновлять стенд.

## Шаг 2. Поднимите версию модели

В `core/scoring.py`:

```python
MODEL_VERSION = "m1-failure-v2"     # было v1
```

Версия пишется в каждый вердикт. Без этого через месяц будет невозможно
понять, какой моделью посчитан конкретный прогноз, — а именно этот вопрос
задают, когда прогноз не сбылся.

## Шаг 3. Пересчитайте вердикты и агрегаты

```bash
python -m scripts.05_generate_verdicts
python -m scripts.10_recall_math
python -m scripts.09_build_analytics
```

## Шаг 4. Зафиксируйте в репозитории

```bash
git add models/ deploy/seed_verdicts.json deploy/seed_analytics.json core/scoring.py
git commit -m "model: переобучение на данных по <дату>"
git push
```

Модель, метрики и вердикты должны попадать в один коммит. Разъехавшись,
они превращаются в загадку: вердикты одной модели, метрики другой.

## Шаг 5. Обновите стенд

```bash
deploy/remote.sh deploy
deploy/remote.sh reset
```

Второй командой обязательно: загрузка вердиктов идемпотентна и при
непустой таблице просто пропускается. Без сброса на стенде останутся
старые вердикты при новом коде — и это не будет видно.

## Шаг 6. Проверьте

```bash
curl 'http://localhost:8080/api/verdicts?limit=1' | grep model_version
```

Должна быть новая версия — поле отдаётся в каждом вердикте именно
для такой проверки. Дополнительно — 162 вердикта в ленте
и диаграммы на странице аналитики, построенные на новых величинах.

## Откат

Модель, метрики и вердикты лежат в git одним коммитом, поэтому откат —
это возврат файлов и повторное развёртывание:

```bash
git checkout <коммит> -- models/ deploy/seed_verdicts.json deploy/seed_analytics.json
deploy/remote.sh deploy && deploy/remote.sh reset
```

# 8. Чего делать не надо

| Соблазн | Почему нельзя |
|---|---|
| Разбить выборку случайно | соседние сутки канала почти одинаковы; модель запомнит канал, метрики вырастут, польза — нет |
| Убрать маскирование массовых базо-дней | 86 % отказных канало-суток приходится на работы бригады; модель выучит график обходов |
| Ориентироваться на ROC-AUC | при доле позитивов 0,05 % он хорош и у бесполезной модели |
| Заполнить пропуски нулями | «нормы ещё нет» и «норма равна нулю» — разные состояния; в коде пропуск заполняется значением −1, невозможным для отношения |
| Увеличить долю позитивов ради красивых метрик | прореживание меняет абсолютную вероятность; ранговые метрики честны, абсолютная — нет |
| Поставить модель, не прошедшую проверку аддитивности | карточки будут объяснять не то решение, которое принято |
